# Надёжная доставка и наблюдение процессов

[Документация](../README.ru.md#документация)

Перед HTTP-доставкой обёртки сохраняют очищенные события в `<HARNESSCOPE_DB_PATH>.outbox.sqlite3`. Отдельная очередь SQLite использует WAL и FULL synchronous. Запуск дочернего процесса не ждёт старта сервера и сети; stdin/stdout/stderr и код выхода сохраняются. Перед завершением обёртка выполняет ограниченную доставку; недоступность телеметрии не меняет результат агента.

При конкуренции writers соединение очереди ждёт до пяти секунд. Конкурирующая первая инициализация повторяет BUSY/LOCKED с новым соединением, включая ошибки настройки WAL, которые могут обходить SQLite busy handler. Исчерпание ожидания и ошибки хранения явно видны в stderr и не меняют код дочернего процесса. Существующая очередь остаётся на диске.

## Восстановление

Используйте одинаковые `HARNESSCOPE_DB_PATH` и loopback-адрес для обёрток и `serve`. Сервер доставляет пакеты каждую секунду, включая оставленные завершившейся или упавшей обёрткой, и независимо собирает нативные источники. Штатное завершение дожидается обоих workers. Сам этот механизм не устанавливает системную службу, планировщик или автозапуск ОС.

- Адресат — нормализованный HTTP origin. `localhost` и `127.0.0.1` используют общего адресата; остальные loopback-адреса и порты разделены.
- Worker обёртки доставляет свой поток через `POST /api/v1/delivery`. Сервер с другой БД не читает очередь автоматически: верните исходную конфигурацию или используйте `outbox flush`.
- Пакеты одного runtime не обгоняют друг друга. Независимые потоки продолжаются при ошибке одного.
- Lease на 30 секунд защищает claims разных потребителей. После аварии lease истекает. Commit сервера и ack outbox раздельны: потерянный ack вызывает повтор. Обычные события дедуплицируются по ID, heartbeat обновляется только более новым временем.
- `/delivery` фиксирует весь пакет либо откатывает его; ответ содержит точный упорядоченный список подтверждённых ID. Один успешный HTTP-статус пакет не удаляет. `/events` сохраняет результаты по отдельным событиям.
- Задержки повтора растут от 2 до 60 секунд и переживают рестарт. HTTP 400/413/422 и неверные связи блокируют поток до явного повтора; временные ошибки остаются в очереди. Retry now снимает задержки/блокировки, но не отменяет активный claim и не удаляет события.

```sh
harnesscope outbox status
harnesscope outbox retry
harnesscope outbox flush
```

`flush` пробует до 100 доступных пакетов и возвращает ненулевой код, если что-то осталось, включая leased/delayed/blocked. Для немедленного повтора сначала используйте `retry`. Команды работают с настроенными путём БД и URL; `status` доступен без сервера. Метаданные очереди видны в **Monitor**.

Для намеренной офлайн-работы задайте `HARNESSCOPE_AUTOSTART=0`. События всё равно сохраняются. Отключается только автоматический запуск, не сбор и не доставка уже работающему серверу.

## Семантика heartbeat

Пока `try_wait` подтверждает, что непосредственный дочерний процесс не завершён, обёртка каждые 15 секунд пишет `runtime.heartbeat`, связанный с новым UUID runtime, а не переиспользуемым PID. Последнее наблюдение хранится в `runtime_observations` схемы v5; heartbeat не заполняет журнал сырых событий. Первое наблюдение создаётся после успешного spawn.

Monitor разделяет результат процесса и свежесть наблюдения:

| Статус | Значение |
| --- | --- |
| FRESH | Последнему наблюдению не больше 45 секунд |
| STALE | Наблюдений не было 45 секунд; могла остановиться обёртка, сервер или машина |
| UNMONITORED | Нет heartbeat или статуса работающего процесса |
| CLOCK SKEW | Наблюдение более чем на 5 секунд в будущем; проверьте часы |
| ENDED | Есть записанное время завершения |

Свежесть основана на **времени наблюдения**, не доставки. Старый офлайн-heartbeat не делает процесс свежим; старые записи не заменяют новые, поздние не открывают завершённый runtime. Отсутствие heartbeat не означает FAILED/COMPLETED. Наблюдатели нативных журналов исключены: их состояние в Sources. GUI-launcher обозначает только launcher, не отсоединённый редактор. Monitor показывает до 200 runtimes, сначала незавершённые.

## Лимиты

Общий бюджет payload очереди — 256 MiB для всех адресатов; до 1 MiB на событие, до 100 событий / 1 MiB на пакет. Старые записи не вытесняются. Полный диск, отсутствие прав, слишком большой объект или исчерпание бюджета дают предупреждение stderr, а агент продолжает работу. Не зафиксированные события восстановить нельзя. Сборщик не является supervisor перезапуска агентов; авария до записи может оставить неполное наблюдение.

SQLite может сохранять выделенные страницы после доставки: бюджет payload не ограничивает размер БД/WAL жёстко. Очистка секретов — best effort, не абсолютная гарантия. Не публикуйте очереди и сырые БД. Большие многодневные офлайн-нагрузки ещё не проверены.

## Работа с панелью

- Шапка: навигация, локальное соединение, пауза/возобновление UI polling. Сбор при паузе продолжается. Настройки меняют плотность и загружают необязательные demo.
- Executions: основные фильтры видны, дополнительные раскрываются. Фильтры/страница в URL. Таблицы desktop и мобильные карточки ведут к тем же данным. Назад из карточки восстанавливает фильтры.
- Карточка: основные факты, раскрываемые токены, оценка, компоненты, Git, агенты и поиск событий. Payload изначально свёрнут; черновики оценок переживают polling и смену вкладок.
- Sessions: любые runner names, URL-фильтры, пагинация, мобильные карточки, доступные ссылки и подписи PROCESS/TURN.
- Sources: боковая форма добавления, фильтр пути, компактные статусы, раскрываемые checkpoints. Monitor: свежесть процесса и диагностика очереди.
- Overview: сравнения групп становятся карточками на узких экранах; экспорт сохраняет выбранные фильтры.

Размер payload поддерживают транзакционные SQLite-триггеры. Существующая очередь пересчитывается один раз при открытии; вставки, ack и rollback поддерживают точный бюджет 256 MiB без перечитывания всех пакетов при каждом добавлении. Файлы могут быть больше из-за SQLite/WAL и свободных страниц. См. [воспроизводимые замеры](PERFORMANCE.ru.md).

Backup основной БД не включает ожидающую доставку. Перед переносом доставьте очереди всех адресатов и сохраните оригинальную БД/outbox до проверки восстановленной истории: [резервное копирование](BACKUPS.ru.md).
