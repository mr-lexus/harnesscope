# Архитектура Harnesscope

[Документация](../README.ru.md#документация)

Harnesscope — локальная кроссплатформенная утилита телеметрии AI-агентов разработки. Она прозрачно оборачивает CLI, детерминированно собирает метаданные выполнения и окружения без внешних языковых моделей, записывает их в SQLite и предоставляет встроенную веб-панель и HTTP API.

## 1. Поток данных и архитектура выполнения

```text
Обёртка Codex    ───┐
Обёртка Copilot  ───┤ HTTP JSON
Обёртка OpenCode ───┤ POST /api/v1/events
Другие адаптеры  ───┤
                   ↓
         Сервер Harnesscope (Axum)
         ├─ Приём и валидация
         ├─ Корреляция: resume сессий, атрибуция
         ├─ Очистка секретов и дедупликация SHA-256
         ├─ SQLite: WAL, внешние ключи, один writer
         ├─ HTTP REST API /api/v1/*
         └─ Встроенный React UI: Mantine + TanStack Query
```

- **Один writer основной БД:** CLI-обёртки не пишут в неё напрямую, а отправляют HTTP-телеметрию локальному серверу.
- **Изоляция ошибок:** недоступный или неисправный сервер вызывает предупреждение обёртки, но не останавливает команду агента.
- **Один сервер:** Axum слушает только localhost, по умолчанию порт 4242; управляет транзакциями, внешними ключами, API и SPA.

## 2. Иерархия сущностей

```text
RuntimeInstance (процесс: PID, argv, начало/завершение)
      │ RuntimeSessionBinding: START, RESUME
      ▼
   Session (нативный диалог, переживает перезапуск процесса)
      ▼
  Execution (наблюдение PROCESS или TURN от адаптера)
      ├── AgentInstance (главный агент / подагенты)
      ├── GitSnapshot (BEFORE / AFTER, файлы и diff stat)
      ├── ExecutionComponent (MCP, скиллы, плагины: CONFIGURED / INVOKED)
      └── Events (хронология телеметрии)
```

1. **RuntimeInstance** — конкретный процесс ОС, например `codex` или TUI `opencode`: PID, cwd, аргументы, время начала/завершения, код выхода.
2. **Session** — логический диалог разработчика с агентом. **Остановка процесса не равна завершению сессии.** При возобновлении с тем же нативным ID, например `codex resume <SESSION_UUID>`, используется прежняя Session.
3. **RuntimeSessionBinding** — явная связь процесса и сессии с причиной `START`, `RESUME`, `ATTACH`.
4. **Execution** — единица анализа: наблюдение PROCESS либо TURN, подтверждённый адаптером. В сессии одно или несколько выполнений.
5. **AgentInstance** — главный агент с ролью вроде `coder`/`architect` либо специализированный подагент, например `reviewer`/`test-writer`.
6. **ExecutionComponent** — связь выполнения с инструментами, MCP-серверами, скиллами и плагинами, с явными состояниями `CONFIGURED`, `DISCOVERED`, `LOADED`, `INVOKED`, `UNKNOWN`.

## 3. Основные решения

### Сессия переживает перезапуск процесса

Разработчик может закрыть терминал и позже продолжить тот же диалог. Соответствие сессии одному процессу раздробило бы историю и исказило анализ. Связь по нативным ID сохраняет непрерывность.

### Worktree — атрибут, а не родитель

Несколько агентов, сессий и выполнений могут одновременно работать в одном worktree, на разных ветках или в разных worktrees. Родительская сущность worktree ошибочно объединила бы независимые запуски. Поэтому worktree — атрибут контекста; при пересечении выполнений атрибуция Git получает `AMBIGUOUS`, при изолированном выполнении — `OBSERVED`.

### Локальная SQLite

- Не требует Docker, PostgreSQL и отдельного обслуживания БД.
- WAL допускает параллельное чтение и короткие последовательные записи: `PRAGMA synchronous = NORMAL;`, `PRAGMA busy_timeout = 5000;`.
- ACID-транзакции и внешние ключи защищают целостность связей.
- Основную БД можно читать стандартными SQLite-инструментами. Пути по ОС описаны в [руководстве разработчика](DEVELOPMENT.ru.md); состав переносимой копии с внешними объектами — в [резервном копировании](BACKUPS.ru.md).

### Когда понадобится PostgreSQL

В локальный MVP он не входит. Возможные причины перехода: общая телеметрия десятков удалённых машин, командная панель; RBAC, несколько организаций и аудит; распределённая трассировка тысяч агентов с разделёнными потоками событий. Слой `src/storage/` отделяет доступ к хранилищу от доменных моделей для возможного добавления другого движка.

## 4. Идентичность, fork и конфликты

### Нативная сессия

Поддерживаемая обёртка извлекает ID диалога из аргументов или окружения. Повторно используется только совпадение имени runner и нативного ID. Без ID сессия остаётся `UNKNOWN`: время, ветка и worktree не доказывают идентичность.

### Fork и родительские связи

Разветвление диалога позволяет проверять разные решения без потери прошлых turns. Если родительские метаданные соотносятся с известной сессией, сохраняются `parent_session_id`, `fork_reason`, `forked_at`. UI даёт ссылку на родителя и список дочерних веток.

### Конфликты сессий

Git фиксирует незакоммиченные изменения, а конфликты workflow определяются отдельно:

1. `CONCURRENT_SESSION_ACCESS`: разные runtimes имеют активные выполнения в одной сессии.
2. `FORK_DIVERGENCE`: активные выполнения пересекаются в известной родительско-дочерней цепочке независимо от порядка старта.
3. `WORKTREE_OVERLAP`: разные сессии имеют активные выполнения в одном worktree; все пересекающиеся выполнения получают атрибуцию `AMBIGUOUS`.

## 5. Одновременный запуск нескольких обёрток

- Каждая проверяет `GET /health` с timeout 200 мс.
- Если сервер недоступен, атомарный файл `server-startup-<port>.lock` в каталоге данных через `create_new(true)` координирует запуск. Окончательное решение остаётся за bind loopback-сокета.
- Остальные обёртки делают ограниченное число health-проверок и подключаются к готовому серверу.
- После координации lock удаляется, чтобы при завершении сервера можно было повторить запуск.

## Ретроспектива и целостность событий

Схема v3 добавила постоянные aliases сессий, область наблюдения выполнения и человеческие оценки. Дедупликация, проекции и запись события выполняются в одной транзакции. Импорт пакета атомарен на уровне отдельных событий: см. [контракт событий](EVENTS.ru.md). Принятие результата не зависит от кода выхода. Overview разделяет сравнимые области и по умолчанию исключает demo. Исторические результаты проверки — в [аудите](AUDIT.ru.md).

### Нативные источники, схема v4

`serve` управляет отменяемой задачей сборщика. Ограниченные блокирующие проходы выполняются вне async-пула. `telemetry_sources` хранит регистрации, `source_files` — состояние парсера и byte checkpoints без содержимого, `execution_usage` — наблюдаемые токены. `CorrelationEngine::process_events_with` фиксирует нативный пакет и checkpoint в одной транзакции. Наблюдатель журнала имеет `surface=transcript`, неизвестный статус процесса и не участвует в конфликтах активных runtimes. См. [нативные источники](NATIVE_SOURCES.ru.md).

### Надёжная доставка и мониторинг

Обёртки сохраняют очищенную телеметрию перед доставкой и наблюдают дочерний процесс каждые 15 секунд. Сервер продолжает доставку после перезапуска. В компактной адаптивной панели есть Monitor, URL-фильтры, мобильные карточки и настройка плотности. См. [доставку, heartbeat и восстановление](DELIVERY.ru.md).
