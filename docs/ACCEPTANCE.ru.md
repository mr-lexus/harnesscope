# Приёмка на реальном устройстве: Codex GUI на macOS

[Документация](../README.ru.md#документация)

Статус: **на реальном macOS GUI ещё не выполнена**. CI и браузерный preview на Windows не закрывают эту проверку. Сначала используйте временный проект и вымышленные задачи. Не используйте настоящие учётные данные в тестах.

## Установка кандидата

Соберите `codex/retrospective-evidence` с Node 24 и стабильным Rust:

```sh
cd web && npm ci && npm run build && cd ..
cargo build --release
bash scripts/install-macos.sh target/release/harnesscope
~/.local/bin/harnesscope capture setup --codex-home "$HOME/.codex"
```

Откройте `http://127.0.0.1:4242/sources`, включите очищенное содержимое для активных и архивных сессий, проверьте hooks и подтвердите доверие к ним в Codex. Зарегистрируйте корень workflow тестового проекта в Evidence. Для нестандартной базы задайте `HARNESSCOPE_DB_PATH` перед setup: созданные hooks фиксируют абсолютный путь. Запишите ОС, версии GUI-приложения и его движка, отдельно установленного `codex --version`, каналы и пути сбора.

## Сценарии и ожидаемые данные

В каждом сценарии фиксируйте нативные ID сессий/turns, ID наблюдений и все пробелы.

1. Требование задачи → уточнение → инструмент → безопасная тестовая ошибка → исправление → проверка → завершение. Принятие результата отметьте вручную: завершение turn не означает принятия.
2. Измените AGENTS.md или тестовый скилл между turns. Проверьте версии и различия. Удалите и создайте файл заново; проверьте явную версию отсутствующего файла.
3. Выполните compaction, прерывание/возобновление, fork, создание/завершение подагента. Проверьте границы, родительские связи и usage. Унаследованная работа родителя не должна увеличивать счётчики потомка. Недоступный размер активного контекста должен оставаться недоступным.
4. Зарегистрируйте локальный [адаптер задач](TASK_ADAPTERS.ru.md). Через MCP трекера в агенте прочитайте задачу, измените вымышленное описание/комментарий и прочитайте снова. Проверьте версии и связи с вызовом/сессией. Проверьте ошибочный ответ и одинаковый ID в двух пространствах имён. При другой структуре ответа измените локальную конфигурацию; неподдерживаемые данные сохраняйте без выдуманных связей.
5. Остановите сборщик, создайте hook-события, запустите снова и проверьте доставку очереди. Повторите доставку и проверьте стабильность ID. Приостановите и возобновите источник с дописанными записями.
6. Используйте синтетический маркер вроде `password=harnesscope-test-canary` в сообщениях, аргументах и результатах. Проверьте его отсутствие в БД, объектах, очереди, логах, backup и экспорте. Прочитайте вымышленный `.env` во временном проекте и проверьте исключение вывода, в том числе отложенного.
7. Экспортируйте задачу/неделю, проверьте backup, восстановите в другой путь, просмотрите историю/контекст/workflow через MCP. Восстановленные нативные источники должны быть на паузе.
8. Восстановите ход нескольких настоящих задач за неделю: требования, workflow, действия, ошибки/переделки, проверки и принятый результат. Для каждого пробела нужна причина.

Повторите основной сценарий в Codex CLI. Проверьте LaunchAgent после входа и перезапуска. Нехватку диска проверяйте на отдельном ограниченном томе, не на системном. Зафиксируйте производительность на больших активных историях.

## Завершение приёмки

Сохраните отчёт с версиями, конфигурацией каналов, результатами сценариев, ссылками на наблюдения и оставшимися пробелами. Обновляйте [матрицу возможностей](CAPABILITIES.ru.md) только для проверенных версий и платформ: один билд не подтверждает остальные. Рабочий скилл ретроспективы запускайте после этой приёмки либо явного согласия пользователя с оставшимися документированными ограничениями.
