# Harnesscope: направление продукта

Дата исследования: 3 октября 2026 года.

## Кому и зачем

Разработчику, который использует несколько AI-агентов и хочет понимать, какие изменения рабочего процесса дают полезный результат: более точные инструкции, другая модель, изоляция в worktree, предварительные тесты, набор инструментов, самостоятельный этап review.

Главный цикл: **записать выполнение → проверить результат → отметить причину переделки → изменить одну часть workflow → сравнить похожие задачи**. Количество запусков само по себе не показывает эффективность. Код выхода 0 не означает, что задача решена правильно. Обнаруженный MCP-сервер не означает, что агент его вызвал.

## Похожие продукты

| Продукт | Сильная сторона по официальным материалам | Что это означает для Harnesscope |
| --- | --- | --- |
| [ccusage](https://ccusage.com/guide/) | Локальный анализ токенов и оценочной стоимости по нескольким агентам | Не делать стоимость единственным центром продукта; добавлять её только по подтверждённым usage-событиям |
| [Langfuse](https://langfuse.com/docs/evaluation/overview) | Трассировка, оценка качества, datasets и эксперименты | Связать технический след с результатом; начать с простой человеческой оценки без LLM-судьи |
| [AgentOps](https://www.agentops.ai/) | Наблюдаемость выполнения агентов и интеграции с агентными фреймворками | Поддерживать общий событийный контракт, не замыкаться на одном CLI |

Это ориентиры, а не исчерпывающий обзор рынка. Предлагаемое позиционирование: **локальная ретроспектива работы coding-агентов с явным качеством доказательств**. Его ценность нужно подтвердить реальными повторами задач, а не объявлять уникальность по списку возможностей.

## Что реализовано

- Overview: период, агент, проект, тип наблюдения, сравнение групп и JSON-экспорт.
- Оценка выполнения: принято, потребовалась переделка, отклонено, ещё не оценено. Заметка и название эксперимента.
- Очередь разбора: незавершённые записи, ошибки, пересечение worktree, отсутствие оценки.
- Видимая полнота данных: известность модели, нативной сессии и границ наблюдения.
- Разделение `PROCESS`, `TURN`, `UNKNOWN`, `DEMO`. Демонстрационные данные исключены из обзора по умолчанию.
- Общий HTTP/JSONL-контракт для сторонних адаптеров; стабильные идентификаторы и безопасный повтор импорта.

## Следующие продуктовые этапы

1. **Два глубоких адаптера вместо десяти поверхностных.** Первый Codex rollout adapter теперь реализован: Sources, turns, tool calls, токены и checkpoint/restart. См. [поддерживаемые форматы и ограничения](NATIVE_SOURCES.md). Проверить Codex на реальных журналах поддерживаемых версий и выбрать второй реально используемый агент. Поддержать нативные журналы или hooks с фикстурами для конкретных версий: реальные turns, tool calls, usage, interruptions, lineage. Прежде чем добавлять интеграцию, зафиксировать гарантии идентичности и модель разрешений на чтение.
2. **Проверка надёжности на реальных нагрузках.** Дисковая очередь, heartbeat, lease и Monitor реализованы; см. [жизненный цикл](DELIVERY.md). Следующий шаг — длительные offline/restart сценарии и большие базы. Переиспользование PID не объединяет runtime; отсутствие heartbeat не означает провал задачи.
3. **Сравнимые эксперименты.** Тип задачи, её сложность, критерии приёмки, потраченное человеком время на переделку, результаты тестов. Для сравнения разделять процессные наблюдения и настоящие turns; показывать размер выборки и пропуски.
4. **Практическая работа с историей.** Экспорт выбранных событий, backup через SQLite backup API, retention с предварительным просмотром удаляемых данных, поиск, список повторяющихся причин переделки.
5. **Командная работа — после локальной полезности.** Аутентификация, разграничение доступа, согласие на отправку содержимого и отдельная модель хранения. Текущий сервер специально не предназначен для сетевой публикации.

## Как провести первую полезную ретроспективу

Выбрать один репозиторий и повторяющийся тип задач. Записать 10–20 запусков. Для каждого отметить пригодность результата и фактическую переделку. Затем изменить одну вещь — например, добавить обязательный failing test перед исправлением — и записать следующую сопоставимую группу с отдельным experiment label. Сопоставить принятые результаты, ошибки, длительность и заметки. Маленькую выборку трактовать как основание для следующего эксперимента, а не как рейтинг моделей.
