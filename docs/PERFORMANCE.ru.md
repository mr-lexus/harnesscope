# Проверка больших историй и восстановления

[Документация](../README.ru.md#документация)

> Документ описывает этап работы от 3 октября 2026 года; статусы и планы ниже относятся к тому этапу. Актуальные возможности и открытые проверки — в [матрице поддержки](CAPABILITIES.ru.md).

Замеры от 2026-10-03, Windows, локальная debug-сборка. Данные синтетические; личные архивы не читались. Это воспроизводимая проверка конкретных сценариев, а не гарантия производительности для любого проекта. Release-сборка, Linux/macOS, миллионы записей и продолжительный soak-тест здесь не измерялись.

## Длинный журнал

Одна сессия и одно выполнение, 10 000 / 100 000 событий с полем текста 128 байт. Импорт атомарными HTTP-пакетами по 500 событий. Задержка — медиана пяти запросов, включая чтение и JSON-декодирование ответа клиентом; используется повторно одно HTTP-соединение. Контроль количества записей и повторная доставка последнего пакета входят в сценарий.

| Метрика | До | После |
|---|---:|---:|
| Карточка выполнения, 10 тыс. событий | 563 мс / 4,31 МБ | 2,2 мс / 1,42 КБ |
| Карточка выполнения, 100 тыс. | 5 537 мс / 43,37 МБ | 14,0 мс / 1,42 КБ |
| Карточка сессии, 100 тыс. | 5 553 мс / 43,37 МБ | 13,3 мс / 1,01 КБ |
| Пиковый рабочий набор сервера, 100 тыс. | 269,3 МБ | 26,3 МБ |
| Импорт 100 тыс. | 37,5 с | 38,2 с |
| Файл основной базы после остановки | 40,7 МБ | 40,7 МБ |

Размеры в таблице десятичные. Health, список выполнений и ретроспектива в этом сценарии остались около 0,6 / 0,8 / 1,5 мс. У него всего одно выполнение: эти цифры не характеризуют отчёты по 100 тысячам отдельных выполнений.

Исправление: журнал исключён из периодически обновляемой карточки и загружается только во вкладке Events. API использует страницы с курсором по ID поступления и поиск по типу/источнику. Новые события с давней временной меткой не сдвигают предыдущие страницы. Одна страница из 50 событий на 100-тысячной истории занимает 21,75 КБ. Счётчики всё ещё требуют подсчёта строк, а поиск — просмотра метаданных соответствующей истории.

Основную базу на 100 003 записях скопировали при работающем сервере, восстановили в новый файл и проверили количество записей и целостность. Совокупное время создания и проверенного восстановления: 3,16 с.

## Офлайн-очередь

100 тысяч событий, пакеты по 100, один поток, 128-байтное текстовое поле. После записи очередь закрывается, открывается повторно и доставляется в новую основную базу. Итоговое количество записей проверяется.

| Метрика | До | После |
|---|---:|---:|
| Запись всей очереди | 53,0 с | 37,9 с |
| Первые 10 тыс. | 3,88 с | 3,74 с |
| Последние 10 тыс. | 6,69 с | 3,97 с |
| Доставка после повторного открытия | 40,2 с | 37,9 с |
| Записано / доставлено | 100 000 / 100 000 | 100 000 / 100 000 |

Прежний контроль лимита перечитывал все накопленные JSON-пакеты при каждой записи. Теперь размер UTF-8-полезной нагрузки хранится в транзакционном счётчике; SQLite-триггеры поддерживают его при добавлении, удалении и изменении пакетов. Существующая очередь пересчитывается один раз при обновлении. Лимит 256 МиБ и запрет вытеснения старых событий сохранены. Это лимит полезной нагрузки, а не размера файла SQLite с индексами, свободными страницами и WAL.

## Проверки корректности

Полный набор: 72 Rust-теста. В том числе восемь реальных одновременных wrapper-процессов без сервера с кодом выхода 7 и последующая доставка; восемь производителей / четыре потребителя очереди на 3 200 событиях; сохранение порядка внутри потока; потеря подтверждения после commit; повторная доставка; частичный UTF-8 и возобновление нативного источника; проверка бэкапа при активной записи и незавершённой транзакции; запрет перезаписи и отказ для повреждённой/чужой/будущей базы. Реальный аварийный перезапуск ОС и физический отказ диска не моделировались.

## Повторение

```sh
cd web
npm run build
cd ..
cargo build -j 1
python scripts/benchmark.py --exe target/debug/harnesscope.exe --output .audit/benchmark.json --check-backup
cargo run --example queue_benchmark -j 1 -- 100000
cargo test -j 1
```

На Linux/macOS убрать `.exe`. Можно менять `--sizes 10000,100000`; скрипт создаёт отдельные временные базы, выбирает свободный loopback-порт и завершает свой сервер. Пиковая память снимается только на Windows. Сырые результаты сохранены в [benchmarks](benchmarks/benchmark-after.json): там же есть `benchmark-before.json`, `queue-before.json`, `queue-after.json`.

Следующие отдельные профили: много коротких выполнений и cohorts, каталоги на тысячи файлов, большие payload, очень длинные офлайн-периоды и длительная конкурентная нагрузка. Список диагностики Sources пока возвращает метаданные всех файлов, а карточка сессии — все её выполнения; эту границу не следует путать с уже ограниченным журналом событий.
