# Нативные источники Codex

[Документация](../README.ru.md#документация)

Harnesscope постепенно читает историю Codex и добавляет нативные границы turns, метаданные модели по turn, вызовы инструментов, отмены/ошибки и наблюдаемые токены. Он не запускает Codex и не вызывает модельные API. Основной сценарий ниже — rollout JSONL; gzip и выбранная SQLite-история описаны в [матрице возможностей](CAPABILITIES.ru.md).

## Подключение

Откройте **Sources**, задайте абсолютный путь к rollout или каталогу. Поиск каталогов рекурсивно включает `rollout-*.jsonl`. Обычно это `sessions` внутри Codex home; используйте фактический путь своей машины. UI не раскрывает `~`.

```sh
harnesscope sources add-codex --path /absolute/path/to/codex/sessions
harnesscope serve
```

Пример Windows:

```powershell
harnesscope sources add-codex --path "C:\Users\YOUR_USER\.codex\sessions"
harnesscope serve
```

CLI `sources` работает с **локальной настроенной БД**, а не `HARNESSCOPE_SERVER_URL`. Задайте тот же `HARNESSCOPE_DB_PATH`, что у сервера. UI управляет БД подключённого сервера.

Импортируется существующая история и новые записи; другие домашние каталоги автоматически не регистрируются и не сканируются. Архивные rollouts подключайте отдельно. Пересекающиеся источники и копии используют стабильные ID: не дублируют выполнения и вызовы.

```sh
harnesscope sources list
harnesscope sources pause SOURCE_ID
harnesscope sources resume SOURCE_ID
harnesscope sources remove SOURCE_ID
```

Remove удаляет регистрацию и checkpoints, сохраняя импортированные данные и оценки. Повторное подключение безопасно повторяет чтение, но не меняет ранее принятые события со стабильными ID.

Один ограниченный проход без HTTP-сервера:

```sh
harnesscope sources scan
```

Повторяйте при `BACKLOG`. За проход — до 200 строк на посещённый файл и 10 изменённых/ошибочных файлов на источник. При ошибках включённых источников код ненулевой; другие файлы могли успешно импортироваться. Это постепенная обработка, не атомарный импорт всего каталога.

## Жизненный цикл

- `serve` управляет одним сборщиком: первый проход сразу, следующий через пять секунд после завершения предыдущего. При backlog интервал 250 мс, чтобы не ждать пять секунд на пакет. Необязательный Windows-установщик создаёт ярлык входа пользователя, не системную службу.
- Смещение, состояние парсера, события и проекции фиксируются **одной SQLite-транзакцией на пакет**. SQL-ошибка откатывает пакет и checkpoint.
- После перезапуска восстанавливаются активный turn и база накопительных токенов. При изменении файла проверяется прочитанный префикс, затем чтение продолжается с byte offset.
- Второй сборщик может конкурировать безопасно: checkpoint использует compare-and-swap смещения внутри транзакции. Устаревший пакет откатывается и повторяется в следующем проходе.
- Пауза останавливает перед следующим пакетом; текущий может завершиться. Shutdown отменяет ожидание и дожидается ограниченной текущей работы.
- Исходные файлы — надёжная входная очередь. Если Codex удалил/ротировал их до чтения, записи восстановить неоткуда. Сохраняйте оригиналы, пока импорт не догонит историю.

Sources показывает последний проход/успех, checkpoints, backlog, ошибки и unmapped. Проход старше 30 секунд обозначается просроченным, не автоматически неуспешным. **Свежесть источника не доказывает работу агента/процесса.**

| Статус файла | Значение |
| --- | --- |
| READY | Прочитаны все полные строки наблюдаемого файла |
| BACKLOG | Возможны оставшиеся полные записи; нужен следующий проход |
| WAITING | Последняя строка без перевода строки; ожидается завершение записи |
| ERROR | Неверный/неподдерживаемый формат, изменение префикса, усечение, ошибка доступа/проекции; checkpoint сохранён |

Незавершённый UTF-8 в последней строке безопасен: декодирования и продвижения offset нет до перевода строки. Даже корректный JSON без завершающего перевода строки остаётся `WAITING`. Повреждённые полные строки не пропускаются молча. Исправьте вход или отключите источник; остальные файлы продолжаются.

При изменении размера/mtime проверяется SHA-256 всего прочитанного префикса. Неизменные размер/mtime — оптимизация, не защита от намеренной подмены. Усечение и изменение префикса отклоняются, история не перезаписывается. Верните оригинал либо изучите отдельную исправленную копию; она тоже не заменяет принятые ID.

Лимиты: 32 MiB на строку JSONL, без ограничения 256 MiB на файл. Пакет — до 200 записей / примерно 8 MiB, одна более крупная запись допустима. Дерево — до 10 000 rollouts / 100 000 элементов. Дочерние симлинки и Windows reparse points пропускаются. Поддерживаются JSONL и gzip JSONL. Подтверждённые родительские префиксы fork сохраняются без начисления унаследованных turns потомку; неоднозначные границы остаются ограничением. Основная [матрица поддержки](CAPABILITIES.ru.md) определяет актуальные возможности.

## Приватность

По умолчанию собираются **только метаданные**: ID thread/turn, время, начальный cwd, модель/effort, имена/call ID инструментов, исходы, токены. Сообщения, инструкции, reasoning, аргументы и вывод не копируются.

**Collect full sanitized evidence** (`--include-content`) отдельно от старых сводок архивирует доступные сообщения, инструкции, аргументы, результаты и контекст. Секретные файлы/непрозрачное содержимое исключаются с причиной. Смена политики в Sources сбрасывает checkpoint для повторного чтения оригиналов; события и оценки не меняются. Метаданные тоже чувствительны: перед включением прочитайте [границы приватности](CAPABILITIES.ru.md).

## Форматы и доказательства

Адаптер — `codex-rollout/v1`; синтетическая фикстура: `tests/fixtures/rollout-codex.jsonl`. Формы сверены с официальными типами Codex через Context7 2026-10-03: `RolloutItem`, `SessionMeta`, `TurnContextItem`, `TurnStartedEvent`, `TurnCompleteEvent`, `TokenUsage`. Rollout — развивающийся внутренний формат, не стабильный публичный API. Поддерживаемая структура важнее строки версии CLI.

- `session_meta.payload.id` определяет текущий thread. В новых файлах `session_id` может обозначать корневой thread и не подставляется вместо `id`.
- Повтор метаданных того же thread идемпотентен, база usage сохраняется. Иной thread внутри одного rollout остаётся явной ошибкой формата.
- `event_msg/task_started` или `turn_started` требует нативный `turn_id` и начинает `TURN`. `task_complete`/`turn_complete` завершает; явная терминальная ошибка даёт FAILED, `turn_aborted` — CANCELLED. EOF не доказывает исход или смерть процесса. Завершение без начала считается unmapped без выдуманного выполнения.
- `turn_context` даёт модель/effort и может дополнить начатый turn. Это метаданные, не доказательство фактически обслужившей каждый ответ модели.
- Function/custom/local-shell вызовы `response_item` считаются по одному на нативный call ID в turn. Поддерживаются прямой item и оболочка `item`. Результат не считается вторым вызовом. Имена `mcp__` показываются как MCP-компоненты.
- `event_msg/token_count.info.total_token_usage` накопительный: из нового значения вычитается предыдущий sample сессии, неотрицательные приращения относятся к текущему turn. Повторы не удваиваются. Fork/history-base сначала устанавливает базу, чтобы не начислять историю потомку. Уменьшение счётчика задаёт новую базу и считается unmapped; неизвестный usage не угадывается.
- Покрытие токенов может быть частичным. Cache включён в input, reasoning — в output. Это не цены, расход подписки или оценка стоимости. Современный `token_usage_record.turn_token_usage` даёт накопительные счётчики turn и имеет приоритет; legacy тогда обновляет только базу и не суммируется снова. Финальный sample может обновить последний завершённый turn. Неизвестный turn или другой thread остаётся unmapped.
- Неизвестные типы считаются unmapped. Известные сообщения/output/compaction/world-state и намеренно пропущенные дубли представления `item_completed` — нет. Неподдерживаемая обязательная структура даёт видимую ошибку файла.
- Журнал использует синтетического наблюдателя `surface=transcript`, UNKNOWN-процесс без PID. Он не считается живым runtime и не создаёт live-worktree/concurrent-runtime конфликты. PROCESS обёртки и нативные TURN раздельны: при сравнении фильтруйте scope.
- Нативная идентичность может связаться с известной сессией обёртки. Известный родитель fork связывается; поздний импорт родителя не восстанавливает связь автоматически. Покрытие унаследованной истории зависит от формата и подтверждённых границ; rollback/retraction не реконструируются. Проверяйте unmapped и матрицу возможностей перед выводами.
- Исторический импорт не запускает Git на сегодняшнем checkout и не приписывает текущие изменения старым turns. При отсутствии repo root фильтр проекта Overview использует **начальный cwd** наблюдателя; последующие изменения cwd остаются только в контекстных наблюдениях.

## API

- `GET /api/v1/collection`: сводное состояние, число включённых источников, проверенных/backlog/ошибочных файлов, преобразованных событий, последний проход, путь БД и версия приложения. Обнаруженный каталог Codex — лишь предложение, не регистрация. Статусы: `NOT_CONNECTED`, `PAUSED`, `STARTING`, `CATCHING_UP`, `COLLECTING`, `OVERDUE`, `NEEDS_ATTENTION`.
- `GET /api/v1/sources`: регистрации и диагностика без состояния парсера.
- `POST /api/v1/sources`: `{ "path": "/absolute/path", "include_content": false }`.
- `PATCH /api/v1/sources/:id`: `{ "enabled": false }` — пауза, `true` — продолжение.
- `DELETE /api/v1/sources/:id`: отключение с сохранением импортированной истории.
- Карточки выполнений содержат nullable `usage`: input, cached input, output, reasoning output, total.
- Нормализованный адаптер может отправлять `execution.context` для модели/effort/summary и `usage.observed` с **накопительными по выполнению** неотрицательными счётчиками. Нужен существующий execution ID. Снимки usage заменяют прошлые, старое время не перекрывает новое. Это не приращения.

## Жизненный цикл процессов

Обёртки используют отдельные outbox и heartbeat: [доставка и мониторинг](DELIVERY.ru.md). Нативные файлы обеспечивают возобновляемый сбор истории, Monitor — наблюдение процессов. Windows-установщик поддерживает явный `-AutoStart` и ярлыки открытия/остановки в «Пуск»: [ежедневная работа](RUNNING.ru.md).
