# Резервное копирование и восстановление БД

[Документация](../README.ru.md#документация)

Снимки схемы 6+ включают все связанные очищенные объекты. Внешние файлы `<database>.objects` проверяются по хешу и по одному встраиваются в переносимую SQLite-копию; для восстановления достаточно её файла. Ожидающие hooks из `<database>.capture`, как и wrapper outbox, не включаются. При переносе офлайн-сборщика сохраните очереди отдельно. Схема 7 также включает локальные конфигурации адаптеров задач. Перед миграцией старой базы на v7 создаётся backup; наблюдения, задачи и отметки сохраняются. См. [подключение сбора](EVIDENCE.ru.md).

`backup create` использует SQLite online backup API и включает зафиксированные записи WAL. Копирование `.db` файловой командой при работающем сервере ему не эквивалентно.

```sh
harnesscope backup create --output /existing/backup-directory/harnesscope-2026-10-03.db
harnesscope backup verify --file /existing/backup-directory/harnesscope-2026-10-03.db
harnesscope backup restore --file /existing/backup-directory/harnesscope-2026-10-03.db --output /existing/data-directory/restored.db
```

Create читает `HARNESSCOPE_DB_PATH` или стандартную базу. Verify и restore используют явно переданные пути. Команды возвращают JSON-отчёт и ненулевой код при ошибке. Родительские каталоги должны существовать. Пути с пробелами заключайте в кавычки.

Снимок включает импортированные события, проекции, оценки, регистрации нативных источников и checkpoints файлов. **Ожидающая доставка outbox, исходные журналы и конфигурация приложения не включаются**; исключения перечислены в каждом JSON-отчёте. Это снимок основной БД, не всей установки.

Для переноса с сохранением всей очереди:

1. Завершите обёртки, поставьте нативные источники на паузу и дайте серверу завершить доставку.
2. Проверьте `harnesscope outbox status`. `harnesscope outbox flush` завершается ненулевым кодом, если для настроенного адресата остались пакеты. У других адресатов отдельные очереди: их тоже нужно доставить.
3. Остановите сервер, создайте и проверьте снимок. Конфигурацию и исходные файлы сохраните отдельно. До проверки восстановленной установки не удаляйте оригинальную БД/outbox.

Обычный снимок на момент времени допускает работающий сервер. Более поздние записи в него не войдут. При busy/locked копирование повторяет шаги до 60 секунд; постоянно меняющийся источник может вызвать timeout. Проверка целостности имеет отдельную длительность и на больших файлах может занять больше времени.

Перед публикацией create и restore выполняют `integrity_check`, `foreign_key_check`, проверяют поддерживаемую схему, обязательные таблицы и число записей. Verify работает только на чтение: не создаёт отсутствующий файл и не мигрирует его. Копирование использует временный соседний файл, а результат публикуется без перезаписи после проверки и синхронизации с диском. Существующие пути, симлинки и SQLite sidecar-файлы назначения отклоняются. Аварийное завершение может оставить неопубликованный `.harnesscope-backup-*`; исходная БД остаётся нетронутой.

Restore всегда создаёт **новый** путь. Поддерживаемые миграции применяются к копии; все зарегистрированные нативные источники ставятся на паузу с сохранением checkpoints. Работающий сервер не переключается, настроенная база не перезаписывается. Для использования результата остановите старый сервер и укажите восстановленный путь:

```powershell
$env:HARNESSCOPE_DB_PATH = 'C:\data\restored.db'
harnesscope serve
```

Linux/macOS: `HARNESSCOPE_DB_PATH=/data/restored.db harnesscope serve`. Проверьте оценки, число записей и пути источников, затем явно возобновите нужные. Наблюдения процессов остаются историческими: restore не перезапускает агентов. Новый путь БД создаёт новый outbox; ожидающие пакеты у старого пути остаются там.

Снимки содержат ту же локальную телеметрию, что БД. Команды не добавляют шифрование или политику удаления. Храните копии в подходящем для этих данных месте.
