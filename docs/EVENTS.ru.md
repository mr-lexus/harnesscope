# Интеграция с любым агентом

[Документация](../README.ru.md#документация)

Harnesscope поддерживает обёртки процессов, нормализованные события адаптеров и [нативный сборщик Codex rollout](NATIVE_SOURCES.ru.md). Два исходных способа приёма:

1. `harnesscope run --runner <name> <command> [args...]` наблюдает **процесс** с наследуемыми терминальными потоками, кодом выхода и Git до/после. Отдельные промпты интерактивного агента и редактор, отсоединившийся от launcher, не наблюдаются.
2. Адаптер отправляет события в `POST /api/v1/events` либо JSON/JSONL для `harnesscope ingest --file events.jsonl`. Это позволяет передать настоящие границы turns и подтверждённые вызовы без привязки БД к провайдеру.

Импорт принимает JSON-объект, массив или JSONL, включая UTF-8 BOM; без `--file` читает stdin. Лимиты запроса/импорта: 2 MiB и 500 событий. Нативные логи сначала преобразуют в этот формат: импорт не разбирает произвольные журналы поставщиков.

## Пример

```sh
harnesscope ingest --file examples/events.jsonl
harnesscope ui
```

Откройте выполнение, оцените результат, задайте связанным запускам общий experiment label и сравните их в Overview. Пример использует `example-agent`: это импортированные тестовые записи, не встроенный demo-набор. Для изолированной проверки задайте временный `HARNESSCOPE_DB_PATH`.

## Контракт события

```json
{
  "event_id": "my-adapter:conversation-123:turn-2:start",
  "timestamp": "2026-10-03T10:00:00Z",
  "event_type": "execution.started",
  "source": "my-adapter/v1",
  "runtime_id": "my-adapter:process-456",
  "session_id": "my-adapter:conversation-123",
  "execution_id": "my-adapter:conversation-123:turn-2",
  "payload": {
    "capture_scope": "TURN",
    "model": "UNKNOWN",
    "prompt_summary": "Add a regression test"
  }
}
```

- `event_id`, `event_type`, `source`: непустые строки до 256 байт. Пространство ID общее для всей БД: добавляйте префикс адаптера и при необходимости аккаунта/источника. Первое принятое событие с ID сохраняется; повтор подтверждает доставку без повторных эффектов и не обновляет оригинал.
- `timestamp`: RFC3339, при записи нормализуется к UTC. Если отсутствует, используется время приёма — подходит живым hooks, но не историческим логам. Исторический адаптер должен передавать исходное время.
- `payload`: JSON-объект. Неизвестные типы остаются событиями хронологии без выдуманных проекций. Неизвестные поля оболочки допустимы, но собственные сохраняемые метаданные помещайте в `payload`.
- Start требует ID соответствующей сущности: `runtime_id`, `session_id`, `execution_id`. Завершение требует тот же ID. Родительские/start-события отправляйте до зависимых/completion, в том числе между запросами.
- `capture_scope`: `PROCESS`, `TURN`, `UNKNOWN`. Время жизни CLI не является turn. Старые записи после миграции остаются `UNKNOWN`; `DEMO` зарезервирован для встроенных примеров.
- `model`: наблюдаемая/запрошенная модель либо `UNKNOWN`. Запрошенная модель не доказывает, что провайдер её использовал или она не менялась внутри процесса.
- Отсутствующий нативный ID диалога остаётся `UNKNOWN`. Не выводите его из cwd, ветки, близости времени или отображаемого названия.

Проекции и запись события фиксируются **в одной транзакции**; ошибка откатывает всё событие. Пакет сначала проверяется целиком, затем применяется **по событиям**, а не одной транзакцией. При ошибке обработки API возвращает HTTP 422 с `event_ids` успешных и `errors` неуспешных событий. HTTP 202 означает обработку всех либо уже принятый повтор. Стабильные ID делают повтор безопасным. Обёртки независимо запускают процесс, сохраняют очищенные события в outbox и используют атомарный `/delivery` ниже. Прямые клиенты `/events` сами сохраняют и повторяют неуспешные импорты.

HTTP-клиенты всегда должны задавать стабильные ID. Файловый импорт без ID хеширует нормализованный JSON: одинаковые записи становятся одним событием. HTTP без ID создаёт случайные идентификаторы и не позволяет дедуплицировать независимые повторы.

## Поддерживаемые проекции

| Событие | Основные поля payload | Смысл |
| --- | --- | --- |
| `runtime.started` | `runner_name`, `runner_version`, `surface`, `pid`, `cwd`, `command_line` | Наблюдение процесса ОС |
| `session.identified`, `session.started` | `runner_name`, `native_session_id`, `title`, необязательный `parent_session_id` | Связь или возобновление диалога |
| `execution.started` | `capture_scope`, `model`, `reasoning_effort`, `prompt_summary`, Git-контекст | Начало процесса или настоящего turn |
| `execution.completed` | `exit_code`, `status`, необязательные `duration_ms`, `error_message` | Завершение; без duration длительность выводится из времени |
| `runtime.stopped` | `exit_code`, `status` | Завершение процесса; неполные выполнения получают UNKNOWN, не успех |
| `agent.started`, `subagent.started` | `parent_agent_id`, `agent_role`, `agent_name`, `model` | Агент внутри выполнения |
| `component.discovered`, `mcp.discovered`, `skill.discovered`, `plugin.discovered` | `name`, `component_type`, `state`, `version` | Конфигурация/обнаружение |
| `component.invoked`, `mcp.invoked`, `skill.invoked`, `plugin.invoked` | `name`, `invocations_count`, `details` | Подтверждённые вызовы; count — неотрицательное **приращение** |
| `git.snapshot` | `snapshot_type`, `repo_root`, `worktree_path`, `changed_files`, `diff_stat` | Наблюдаемый Git; сервер сохраняет неоднозначность атрибуции |
| `config.snapshot` | `config_type`, `raw_content`, `parsed_json` | Необязательные очищенные данные конфигурации |

Сессия идентифицируется парой `runner_name`/`native_session_id`. Если возобновившаяся обёртка передаёт новый локальный ID сессии, постоянный alias направляет её события в прежний диалог. Неимпортированный родитель остаётся в сыром событии без нарушенного внешнего ключа; его поздний импорт не восстанавливает связь автоматически.

## Человеческие оценки и отчёты

- `GET /api/v1/executions/:id/review`: сохранённая оценка либо `null`; нет выполнения — 404.
- `PUT /api/v1/executions/:id/review`: `{"outcome":"ACCEPTED","notes":"...","experiment":"tests-first-v2"}`. Результаты: `UNREVIEWED`, `ACCEPTED`, `REWORK`, `REJECTED`. Notes до 10 000 байт UTF-8, experiment до 120. Сохранение заменяет текущую оценку.
- `GET /api/v1/retrospective?days=30&runner=codex&scope=PROCESS`: отфильтрованные данные, покрытие оценками, группы и очередь разбора. Необязательный `project` — точный путь репозитория; `include_demo` по умолчанию `false`, `days` ограничен 1–3650.
- Overview экспортирует выбранный JSON-отчёт с фильтрами, временем и версией схемы. Это агрегат, **не полный backup БД**. Доля принятых считается среди оценённых выполнений; неизвестные/неоценённые не становятся успехом или ошибкой.

## Локальная безопасность и приватность

Сервер слушает только loopback. Браузеру нужен тот же HTTP origin; чужие origins, cross-site запросы и не-loopback Host отклоняются. Wildcard CORS нет. CLI обходит прокси и не следует redirects. Это локальное однопользовательское приложение, не аутентифицированный сервис для недоверенных локальных пользователей или удалённой команды.

Очистка рекурсивно проходит JSON, распознаёт распространённые секретные поля, токены провайдеров, CLI-присваивания, авторизацию и приватные ключи; также очищает названия сессий и заметки оценок до записи. Это best effort, не гарантия удаления всех секретов/персональных данных. Не помещайте секреты в промпты, ID и payload; проверяйте экспорт перед передачей.

Обёртки не сохраняют полные конфиги без `HARNESSCOPE_CAPTURE_CONFIG=1`, но могут обнаруживать имена компонентов. Универсальные обёртки принимают переносимые метаданные только через `HARNESSCOPE_SESSION_ID`, `HARNESSCOPE_PARENT_SESSION_ID`, `HARNESSCOPE_MODEL`; чужим флагам `-s`/`-m` не приписывается смысл.

Нативный сбор фиксирует checkpoints атомарно с пакетами событий. Обёртки отдельно используют outbox и heartbeat: [нативные источники](NATIVE_SOURCES.ru.md), [доставка и восстановление](DELIVERY.ru.md).

## Атомарная доставка и наблюдения процессов

`POST /api/v1/delivery` принимает массив 1–500 событий с HTTP-лимитом 2 MiB, фиксирует весь пакет и возвращает `{"event_ids":["id-1","id-2"]}` в исходном порядке. Ошибки валидации: 400/422; транзакции: 503 без подтверждения. Повторяются те же ID. Это намеренно отличается от `/events` с отдельными результатами импорта.

`runtime.heartbeat` требует существующий `runtime_id` и RFC3339-время наблюдения непосредственного дочернего процесса. В `runtime_observations` сохраняется только последнее время: повтор безопасен по монотонной метке, это не история сырых событий. Heartbeat не открывает завершённый runtime и не определяет исход задачи. Выделяйте его ID отдельное уникальное пространство.

`GET /api/v1/monitoring` возвращает до 200 наблюдений процессов, общие счётчики outbox и до 100 диагностик ожидающих пакетов. `POST /api/v1/outbox/retry` сбрасывает задержки/блокировки настроенного адресата, не удаляя события и не отзывая lease. Ограничения loopback/origin те же.

## Ограниченная история событий

Карточки выполнений и сессий возвращают `events_total` вместо полного массива `events`. Клиентам прежнего development API нужно запрашивать журнал отдельно:

- `GET /api/v1/executions/:id/events?limit=50&before_id=123&search=tool`
- `GET /api/v1/sessions/:id/events?limit=50&before_id=123&search=tool`

Ответ: `{"items":[...],"total":1234,"next_cursor":73}`. `total` считает все совпадения независимо от страницы. `limit` по умолчанию 50, пределы 1–100. `search` — буквальная подстрока типа/источника события, не payload, до 200 байт UTF-8. Нет владельца — 404; неверный курсор — 400.

Порядок — убывающие ID поступления в БД, не время события: поздняя доставка не сдвигает старые страницы. Без `before_id` возвращается последняя; `next_cursor` ведёт к более ранним поступлениям, `null` означает конец. Новые записи видны при обновлении последней страницы. Общий `total` между страницами может измениться при записи; одна страница и её total читаются одной транзакцией.

UI загружает журнал только во вкладке Events, держит в DOM одну страницу и опрашивает только последнюю. Скрытая вкладка и исторические страницы не опрашиваются. Запросы карточек/истории выполняются на blocking workers, освобождая async HTTP workers.
